# Bleak Plan 08 — QA and Game Testing

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Find every bug before a player does, prove every spec rule and fail-safe with a repeatable test, and own the gate at the end of each milestone.

**Architecture:** Four tiers. T1 unit specs are written by module owners. The Game Tester owns T2 scenarios (scripts that run inside a live Studio server and drive it through `DebugService`), T3 agent playtests (real input through the Studio MCP tools, with screenshots), and prepares T4 human playtests. Bots play whole matches for soak and balance.

**Tech Stack:** TestKit, Studio MCP (`start_stop_play`, `execute_luau`, `character_navigation`, `user_keyboard_input`, `user_mouse_input`, `screen_capture`, `get_console_output`), `Stats` service, MicroProfiler.

**Spec:** `docs/spec/2026-11-13-bleak-game-design.md`, all sections; section 14 in particular.

Agent: **Game Tester**. The Game Tester never fixes product code. It writes
tests and bug reports; owners fix. Every task needs the Studio token unless
it says otherwise.

Rules of evidence:

- A check passes only with output: a scenario result table, a console log with zero errors, or a screenshot.
- "Zero errors" means `get_console_output` has no line at error level from any script under `Server`, `Client` or `Shared`.
- A scenario that passes once is run three times before it counts. A scenario that fails one time in three is a bug (flaky is failing).
- Every bug gets a failing test before it gets a fix (master plan section 10).

### Task Q1: QA scaffolding

**Files:**
- Create: `src/tests/RunScenario.luau`, `src/tests/scenarios/_Kit.luau`
- Create: `docs/qa/BUG-TEMPLATE.md`, `docs/qa/bugs/.gitkeep`, `docs/qa/README.md`, `docs/qa/gates.md`

**Interfaces — Produces:**

```lua
-- A scenario is a ModuleScript named "<Name>.scenario" returning function(k) ... end
-- RunScenario(name: string): { name: string, passed: boolean, checks: number,
--   failures: {string}, errors: {string}, duration: number }
-- RunScenario("*") runs all and returns a list.

k.reset(opts: { difficulty: Difficulty?, bots: number?, seed: number?, stage: number? })
  -- ends any match, resets, starts a new one through DebugService
k.bot(index: number): Bot                    -- see Q2
k.wait(seconds: number)
k.waitFor(description: string, timeout: number, predicate: () -> boolean)   -- fails the scenario on timeout
k.check(description: string, condition: boolean)
k.equal(description: string, actual: any, expected: any)
k.near(description: string, actual: number, expected: number, tolerance: number)
k.noErrors()                                  -- fails if LogService saw an error since k.reset
k.debug                                       -- DebugService
```

`RunScenario` wraps each scenario in `pcall`, captures `LogService.MessageOut`
errors, has a hard timeout of 240 s per scenario, and always resets the
match afterwards.

**Bug template fields:** id, title, severity, build (git commit), found by (tier and scenario or steps), steps to reproduce (numbered), expected (with spec section), actual, evidence (log lines, screenshot path), owner, failing test (path), fix commit, verified by and date.

`docs/qa/gates.md` holds one table per milestone gate (below) with a row per
check, the evidence path and the date.

- [ ] **Step 1:** Write the files. Write `Smoke.scenario`: `k.reset({bots = 1})`, `k.waitFor("phase Dormant", 15, ...)`, `k.noErrors()`.
- [ ] **Step 2:** Run it three times. Expected: `passed = true` each time.
- [ ] **Step 3:** Commit: `test: add scenario runner and QA templates`.

### Task Q2: DebugService and bots

**Files:**
- Modify: `src/server/Services/DebugService.luau`
- Create: `src/tests/scenarios/_Bot.luau`

DebugService exists only when `RunService:IsStudio()`. `ServiceContracts.spec`
checks that `Main.server.luau` does not require it otherwise. A release build
uses `release.project.json`, which has no `Tests`; add a unit spec asserting
that no module under `Server` or `Shared` requires anything under `Tests`.

**Commands:**

```lua
DebugService.startMatch(opts: { difficulty: Difficulty?, seed: number?, bots: number? })
DebugService.endMatch()
DebugService.setStage(stage: number)                 -- releases Wisps instantly up to that count
DebugService.setPhase(phase: MatchPhase)
DebugService.give(player: Player, kind: ItemKind, lit: boolean?)
DebugService.teleport(player: Player, where: Vector3 | string)   -- string = tag or ZoneId
DebugService.setStatus(player: Player, status: PlayerStatus)
DebugService.setLamp(player: Player, on: boolean, beam: boolean, charge: number?)
DebugService.aim(player: Player, at: Vector3)        -- sets the stored aim server-side
DebugService.keeper(): { state: KeeperState, position: Vector3, target: Player?, memory: any }
DebugService.setKeeperState(state: KeeperState, target: Player?)
DebugService.teleportKeeper(where: Vector3 | string)
DebugService.freezeKeeper(frozen: boolean)
DebugService.spawnBrineling(at: Vector3)
DebugService.openCage(cageId: string)
DebugService.unlockAll()
DebugService.fillBrazier(charges: number, lit: boolean)
DebugService.timeScale(scale: number)                -- multiplies dt in service loops (1..10)
DebugService.addBot(): Player-like                   -- see below
DebugService.removeBot(bot)
DebugService.fireRemote(asPlayer, name: string, ...: any)    -- runs the server handler with raw arguments
DebugService.snapshot(): table                       -- every attribute of MatchState, players, NPCs, doors, items
```

**Bots:** real `Player` objects are not available in a single Studio play
session, so a bot is a server-side fake: a character model in group
`Players` plus a table that implements the fields services read (`UserId`
negative, `Name`, attributes via a Folder, `Character`). Services must read
players only through `PlayerStateService`, so a bot registered there is
treated as a player. (Core adds `PlayerStateService.registerFake(bot)` behind
`IsStudio`; the Game Tester asks for it in this task.)

```lua
bot:moveTo(position: Vector3 | string, mode: "Walk" | "Sprint" | "Crouch")   -- yields until arrival or timeout
bot:interact(target: Instance, holdSeconds: number?)       -- Begin, wait, expect completion
bot:setLamp(on: boolean); bot:beamAt(target: Vector3 | Instance, seconds: number)
bot:drop(); bot:use(); bot:leave()                          -- leave simulates PlayerRemoving
bot.status(): PlayerStatus; bot.held(): ItemKind?; bot.position(): Vector3
```

- [ ] **Step 1:** Implement. Write `Bots.scenario`: a bot walks from `PlayerSpawn` to the Brazier, picks up a canister given by `give`, pours, and the Brazier is lit.
- [ ] **Step 2:** Run three times. Commit: `test: add debug service and bots`.

### Task Q10: Performance and smoothness

**Files:** Create `src/tests/PerfProbe.luau`, `docs/qa/perf.md`.

`PerfProbe` (client and server parts, Studio only) records for 60 s: frame
time mean and 99th percentile, server heartbeat mean and minimum, instance

`Instance.new` calls in client controllers per second (by wrapping the pool
constructors). It reports a table.

Measure at: the six reference viewpoints standing still; a sprint lap around
the Yard; a 4-bot chase at stage 9 with 6 Brinelings in the Cannery; the
`Won` ending. Compare with spec 16.3.

Smoothness checks (T3 frame sequences, 10 captures 0.1 s apart):
- Keeper movement: position difference between consecutive frames never jumps by more than 2 × expected (speed × 0.1) unless a teleport fail-safe fired.
- Door swing: no frame shows the door intersecting a character.
- Camera: no roll or pitch snap entering or leaving sprint, crouch, downed or carried.
- UI: prompt appears within 0.1 s of targeting.

Memory leak check: run `FullMatch` (a) five times on one server; server and
client memory after match 5 are within 10% of after match 1; the count of
connected signals in `Signal` (add a Studio-only counter) is equal.

### Task Q12: Human playtest

**Needs:** H-8.

**Files:** Create `docs/qa/human-playtest.md`.

Prepare the checklist for 2–4 real players on the "Bleak Test" experience
(published from Studio by the user), 3 sessions (one per difficulty):

1. All players load into the Dock within 12 s. Everyone sees everyone.
2. Ready-up, difficulty change and start work; a non-host cannot start.
3. Each player sees the others' lamps and beams pointing the right way.
4. Two players grab the same item at once: one gets it.
5. A player is grabbed: the others see the proxy on the Keeper; the victim sees the carry view; revive works.
6. One player closes their client while carried, while holding a key, during a revive. Play continues.
7. A late joiner spectates and joins the next match.
8. Voice chat (if enabled) is positional and the Keeper does not react to it.
9. Win once, lose once. Results and XP are right. XP is still there after rejoining.
10. Each player answers: any moment you did not know what to do? any moment that felt unfair? any stutter or rubber-banding? any sound that was wrong or missing?

Also network conditions: one session with the Studio network simulator or a
real poor connection (ask the user) at 150 ms latency: interactions still
resolve correctly; the hold ring matches completion.

- [ ] Give the checklist to the user. Record answers. File bugs. Commit: `test: add human playtest results`.
